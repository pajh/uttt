# Local Ultimate Tic-Tac-Toe rig

This is a development repository for an Ultimate Tic-Tac-Toe CodinGame bot.
The supported code is deliberately separated from recovered snapshots and
one-off analysis tools:

- [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) explains the directory layout,
  board model and search flow.
- [`docs/DEVELOPMENT.md`](docs/DEVELOPMENT.md) gives the everyday build, test
  and experiment process.
- `src/bots/`, `src/engine/` and `src/rig/` contain supported code.
- `src/legacy/` preserves historical sources; it is not the place for new work.

Run the regression suite before a behaviour change:

```sh
make test
```

Build and play a baseline match batch from this directory:

```sh
make
./bin/gamerig -G10
```

The default matchup is the unchanged historical `src/legacy/orig.c` bot against
`src/bots/ai_random.c`. Starts alternate each game. This is a process-based
rig: each bot receives CodinGame-style turn input on stdin and writes its move
to stdout. stderr remains available for bot diagnostics. No recovered direct-call
bot API is used.

Select either executable and a local response guard:

```sh
./bin/gamerig -G10 --p0 ./bin/orig --p1 ./bin/ai_random --timeout-ms 2000
./bin/gamerig -G10 --p0 ./bin/ai_random --p1 ./bin/ai_random
```

The timeout is a local hang guard, not a simulation of CodinGame's server performance or timing rules. By default it allows 1,200 ms for each bot's first response and 120 ms thereafter. Responses above the nominal 1,000/100 ms limits produce logged warnings and CSV overrun flags but remain valid within this 20% grace. Exceeding the grace cutoff forfeits that game; the batch continues and retains earlier results. `--timeout-ms` overrides the cutoff for all turns. Local compile options can be set through `CFLAGS` and `LOCAL_ARCH`; the bots' existing source pragmas are unchanged. To rebuild with different local options, use `make -B CFLAGS='-Wall -g -O0'`, for example. Source pragmas can override command-line optimization choices.

Scores label p0 as Player 1 and p1 as Player 2 regardless of starting order. Illegal/malformed moves, EOF and response timeouts forfeit the game; failure counts appear separately. Exit status is 0 for a clean batch, 2 if a bot fails during play, and 1 for setup/usage errors. The rig closes pipes, terminates and reaps both bot processes after every game.

`src/bots/ai_minimax.c` has received correctness repairs and is available through `--p0 ./bin/ai_minimax`; the 10-game pilot against unchanged `src/legacy/orig.c` finished 6–3–1 with no forfeits. `src/legacy/ai_base.c` and `src/legacy/ai_heuristic.c` need their historical board API recovered or migrated before they build.

Generate the modular bot's single-file submission without replacing either recovered submission snapshot:

```sh
make submission
```

The result is `bin/submission.c`, generated by `subst` from
`src/bots/ai_minimax.c`, `src/engine/board.h`, and `src/engine/hashmap.h`.
Generation does not make the unfinished modular bot arena-ready.
`src/legacy/orig.c` and recovered `src/legacy/cg_tictac.c` are preserved. The
obsolete copy-to-home-directory action has been removed from the makefile.

See REVIEW.md for the original inventory and code review. Its initial build and rig observations describe the recovered tree before these repairs.

## Parallel benchmarks

Run four local batches with one configuration:

```sh
fish scripts/multi-rig.fish
```

The final report is always `reports/latest-analysis.html`. Earlier reports are
numbered, such as `reports/latest-analysis.1.html`. CSV data and logs for the
current run live in `work/latest/`; older runs are numbered in `work/latest.N/`.
To rebuild a report without playing games, use `fish scripts/resummarize.fish` or
pass a saved run directory. See [`scripts/README.md`](scripts/README.md).

For four live coloured worker lines on a local terminal, run
`fish scripts/multi-rig.fish --interactive`. The top of `scripts/multi-rig.fish` holds the two
bot commands, worker count and games per worker. GitHub uses the same fish
script in plain-output mode and sets its game count through the workflow input.
For the guarded 1,000-game GitHub launch, status check, and download commands,
see [`scripts/README.md`](scripts/README.md#standard-1000-game-github-run).

## Starting-move experiments

Compare the normal opener with the 15 empty-board symmetry policies:

```sh
python3 find-starting-classes.py --games 200 --jobs 4 --seed 20261001
```

`M` means middle, `D` diagonal/corner, and `C` cardinal/edge. `S`, `O` and `A` split same-category pairs into same, opposite and adjacent; `N` and `F` split mixed diagonal/cardinal pairs into near and far. For example, `DDS` selects the same inner diagonal as the outer grid and therefore sends the opponent back to our starting grid. Player 0 is always our bot and always starts. `BASE` supplies the normal 81 legal moves and lets the bot choose. Every policy reuses the same seed schedule, and every game row records the exact opening row, column, grid and cell sampled or chosen.

The **Starting move class finder** GitHub Actions workflow defaults to 200 games for each of `BASE MM MD MC DM DDS DDO DDA DCN DCF CM CDN CDF CCS CCO CCA`: 3,200 games total with four concurrent policies. It uploads the policy summary, exact-opening sample frequencies, raw game tables, verified bot identities and logs as one artifact. `find-starting-moves.py` remains available for a later exhaustive 81-coordinate experiment.

Use the small `gh` wrapper to submit and retrieve hosted work without navigating the Actions UI:

```sh
./github-experiment.sh launch 200 20261001
./github-experiment.sh list
./github-experiment.sh watch RUN_ID
./github-experiment.sh fetch RUN_ID
```

The workflow is manual-only, so ordinary pushes cannot start expensive jobs accidentally. `fetch` stores the artifact directly under `published-results/run-RUN_ID/` and prints its summary.
